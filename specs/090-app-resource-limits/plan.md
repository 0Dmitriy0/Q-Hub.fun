# Implementation Plan: Ліміти пам'яті й процесора для програми

**Branch**: `090-app-resource-limits` | **Date**: 2026-11-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/090-app-resource-limits/spec.md`

## Summary

Програма має вкладатись у 1,5 ГБ пам'яті, 5 % процесора у фоні під час гри, 10 % під час користування й 1 % у простої. Підхід: спершу виміряти (заміру «до» немає), потім додати журнал споживання й сторожа пам'яті, далі прибирати підтверджені заміром втрати — за спаданням ваги й із повторним заміром після кожної зміни. Найімовірніше джерело навантаження у фоні — повний кадр екрана, який раз на 0,7 с копіюється між процесами заради маленької ділянки HUD ([research.md](./research.md), H1). Швидкість дій гравця й точність розпізнавання не погіршуються.

## Technical Context

**Language/Version**: JavaScript (CommonJS) у головному процесі, Node.js у складі Electron 37.10.3; інтерфейс вікон — TypeScript + React (спільна збірка сайту, `npm run build:app`)

**Primary Dependencies**: Electron 37, tesseract.js 6.0.1 (розпізнавання в робочих потоках), koffi 2.9 (фокус гри), @supabase/supabase-js. Нових залежностей немає

**Storage**: локальні файли в теці даних програми: новий `usage.log`; наявні журнали й налаштування без змін. База даних не зачіпається

**Testing**: `node --test` (`desktop/src/*.test.cjs`) для чистої логіки; наявні фікстури розпізнавання як захист від регресії; ручний еталонний сценарій із `desktop/scripts/measure.ps1` ([quickstart.md](./quickstart.md))

**Target Platform**: Windows 10/11 x64, поруч із GTA V / RAGE MP

**Project Type**: desktop-app (Electron), частина монорепозиторію із сайтом

**Performance Goals**: пам'ять ≤ 1500 МБ завжди; процесор (частка всього процесора, усі процеси програми разом): простій ≤ 1 %, фон ≤ 5 %, користування ≤ 10 % у середньому, сплески ≤ 25 % до 5 с

**Constraints**: дії гравця не повільніші ніж на 10 % (FR-008); ті самі результати розпізнавання на фікстурах (FR-009); кадр — лише знімок екрана (FR-013); без самоперезапуску й системної стелі (FR-006); журнал лише локально (FR-012)

**Scale/Scope**: один ПК, 6–8 процесів програми; ~6300 рядків у `desktop/src`; зміни в `main.cjs`, `vision.cjs`, `grab.html`, `session.cjs`, два нові файли логіки з тестами, один скрипт заміру

**Невідоме, яке закриває перший крок (не блокує план)**: поточне споживання в кожному стані; одиниця `percentCPUUsage` (весь процесор чи ядро) — [research.md](./research.md) R1

## Порядок реалізації (для /speckit-tasks)

1. **Інструменти заміру**: `measure.ps1` і журнал споживання (US4) — `usage.cjs`, `usage.log`, запис тривалостей дій у режимі заміру. Жодної оптимізації на цьому кроці: інакше «до» вже не буде «до».
2. **Замір «до»** за сценарієм; таблиця в `measurements.md`; звірка журналу із зовнішнім заміром. Потребує власника в грі для трьох станів із чотирьох.
3. **Сторож пам'яті** (US2, FR-006): пороги, дії, перевірка на малих порогах.
4. **Фон** (US1, суворий ліміт): M2, далі H1–H6 за виміряною вагою; після кожної — замір стану «фон» і тести.
5. **Довгий сеанс** (US2): M1, M4, M5 за результатом 4-годинного заміру.
6. **Користування** (US3): звірити сплески; що не вкладається без сповільнення — записати винятком, а не сповільнювати.
7. **Замір «після»**, запис у журналі оновлень, перезапуск програми з коду.

## Ризики

- **Замір залежить від власника**: без живої гри немає чисел для фону й користування — робота стоїть на кроці 1.
- **H1 зачіпає найчутливіше місце** — шлях кадру до розпізнавання. Захист: фікстури, порівняння часу кадру скупника в `vision.log` до/після, запасний шлях (повний кадр) лишається.
- **H2 може не спрацювати**: HUD малюється поверх світу гри, і білі пікселі фону можуть мінятись щокадру — тоді пропуск не дасть виграшу. Перевіряється до впровадження.
- **Ліміт 5 % може бути недосяжним на слабких ПК** — у специфікації це орієнтир, не гарантія.
