# Implementation Plan: Правдивий склад і зручніший облік

**Branch**: `030-stock-ledger` | **Date**: 2026-10-31 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/030-stock-ledger/spec.md`

## Summary

**US1 — списання продажу скупнику.**
- Автооблік (`autoRecords` у `desktop/src/main.cjs`) уже пише «Продаж фарму». Тепер він повертає `id` цього запису, а зір (`vision.cjs`) додає до продажу скупника й ціни, які щойно прочитав у його вікні.
- Main тримає продаж як **пропозицію** (10 хв) і віддає її плашці.
- Плашка рахує кандидатів чистою функцією `src/lib/saleGuess.ts`: один товар без остачі, «Продати все» або нестача → «нафармив + продав».
- Після Enter main пише угоди з `tx_id` наявного запису. Нового запису обліку не створюється: це той самий механізм, що вже є в `insertDeal`, тільки без власного запису.
- «Скасувати» (10 с) видаляє лише ці угоди.
- Міграція не потрібна: `deals.tx_id` є з 0001.

**US2 — склад.** `advise()` з `src/lib/advice.ts` уже рахує по товару найкращого скупника, прибуток проти собівартості, положення ціни й свіжість (дашборд). Склад показує це по кожному рядку. До нього додаються:
- поріг «краще почекати» (pos < 40);
- блок «Не купує жоден скупник» — те, що `advise` зараз мовчки пропускає.

**US3 — облік.** Три чисті функції, які однаково працюють на сайті й у програмі:
- `src/lib/txFilter.ts`: фільтри й сума;
- `src/lib/txCsv.ts`: CSV з `;` і BOM;
- `src/lib/perHourByCat.ts`: час за проміжками між записами в межах сесії, ≤ 30 хв, < 15 хв → «замало даних».

**Попутна вада.** «Угоди» в кабінеті, видаляючи угоду, видаляють і прив'язаний запис обліку (`DealsPage.tsx:49`). Для списання автоматичного продажу це стерло б справжні гроші (FR-003a). Запис тепер видаляється лише тоді, коли він створений самою угодою (`source = 'deal'`).

## Technical Context

**Language/Version**: TypeScript 5 (сайт, кабінет і плашка — React + Vite), CommonJS Node / Electron (`desktop/src/*.cjs`)
**Primary Dependencies**: `@supabase/supabase-js`; без нових
**Storage**: Supabase Postgres — `transactions`, `deals` (`tx_id`), `game_sessions`; схема без змін
**Testing**: `vitest` (сайт, `src/lib/*.test.ts`), `node --test` (програма, `desktop/src/*.test.cjs`)
**Target Platform**: сайт q-hub.fun (кабінет — перегляд), Q-Hub Desktop (плашка Alt+Q, кабінет у програмі)
**Project Type**: веб-сайт + desktop-програма над спільною базою
**Performance Goals**: пропозиція в плашці ≤ 1 с після запису автообліку; фільтр 5 000 записів — без помітної затримки
**Constraints**:
- без підтвердження гравця склад не змінюється (принцип IV);
- скасування не чіпає запис про гроші;
- кабінет на сайті лише для перегляду;
- старі записи без `tx_id` працюють як раніше.

**Scale/Scope**:
- 4 нові модулі в `src/lib` з тестами;
- правки в `main.cjs`, `vision.cjs`, `Bar.tsx`, `StockPage.tsx`, `LedgerPage.tsx`, `DealsPage.tsx`, `styles.css`, журналі.

## Constitution Check

*GATE: перевірено до Phase 0 і після Phase 1.*

| Принцип | Як дотримано |
|---|---|
| I. Зовнішній інструмент | гра не зачіпається; програма лише читає екран, як і зараз |
| II. Права — у базі | нових таблиць і політик немає; угоди пишуться під RLS «угоди персонажа» |
| III. Знімки приватні | знімки не зберігаються; ціни беруться з уже розпізнаного тексту |
| IV. Перевірені дані | склад змінюється лише після Enter (FR-001); кількість вгадується лише при поділі без остачі (FR-002); «чистий за годину» каже «замало даних», а не вигадує |
| V. Програма лише додає | програма додає угоди. «Скасувати» видаляє **лише щойно додані нею самою** угоди за 10 с — див. Complexity Tracking |
| VI. Тести | `saleGuess`, `txFilter`, `txCsv`, `perHourByCat`, пороги `advise`; `DealsPage` — правило видалення запису |
