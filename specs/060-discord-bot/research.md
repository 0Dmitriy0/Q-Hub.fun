# Research: Discord-бот Q-Hub (060)

## R1. Постійний бот чи REST

- **Decision**: лише Discord REST API v10 з токеном бота (`Authorization: Bot <token>`): `POST /channels/{id}/messages`,
  `POST /channels/{id}/messages/{mid}/crosspost`, `GET /channels/{id}` (перевірка доступу), `GET /users/@me/guilds`
  (список серверів, US4 AC2).
- **Rationale**: зараз бот лише пише; постійний процес із Gateway потрібен тільки для читання повідомлень (майбутня
  функція). Edge Function без сервера — нуль інфраструктури й нуль витрат.
- **Alternatives**: окремий процес на VPS / Railway (discord.js) — потрібен хостинг 24/7 заради одного POST; відкладено до
  функції читання. Вебхук каналу — не вміє `crosspost` і не дає «той самий бот на інших серверах»; відкинуто.

## R2. Що запускає публікацію цін

- **Decision**: `pg_cron` щохвилини → `pg_net.http_post` на функцію `discord-bot` з `x-sync-secret` (дія `tick`).
  Секрет і адреса — у `vault` / налаштуванні бази, не в міграції.
- **Rationale**: SC-001 (≤ 2 хв). GitHub Actions cron має мінімум 5 хв і часто запізнюється на 10+ хв.
- **Alternatives**: тригер на кожну зміну одразу кличе функцію — немає вікна збирання (FR-004); відкинуто. Запасний
  шлях, якщо власник не ввімкне розширення: workflow `discord-tick.yml` кожні 5 хв (повільніше, але працює).
- **Залежність від власника**: увімкнути `pg_cron` і `pg_net` (Supabase → Database → Extensions) — одна дія.

## R3. Вікно збирання й ліміт пересилань

- **Decision**: зміни з `discord_outbox` (стан `new`) збираються, доки від найстарішої не минуло `window_min` хвилин
  (за замовчуванням 5). Перед публікацією функція рахує свої публікації в канал цін за останню годину; якщо вже
  `crosspost_per_hour` (за замовчуванням 10, налаштування) — чекає, і все нове йде в наступне повідомлення (Edge Cases:
  «одне більше зведення, а не губить»). Ключ публікації — `prices:<id найстарішої події>`: повторний `tick` не дублює.
- **Rationale**: FR-003, FR-004, SC-002. Числа — у `discord_bot`, щоб міняти без релізу (як `price_rules`).
- **Перевірено (T001, 2026-11-04)**: в API-документації (`docs.discord.com` → Message → Crosspost) ліміту немає — він у довідці Discord про канали-оголошення (10 публікацій на годину на канал); лишаємо 10 за замовчуванням, а 429 обробляє `discord.ts`. Для crosspost власного повідомлення досить `SEND_MESSAGES`; `MANAGE_MESSAGES` у запрошенні — запас, не обов'язковий.

## R4. Формат повідомлення цін

- **Decision**: embed на кожного зміненого скупника (до 10 embed в одному повідомленні; більше — кілька повідомлень
  того самого вікна, з тим самим ключем + номером частини). Embed: назва скупника й місце, рядки «Предмет — ціна ▲ +50 /
  ▼ −20 / нове», «Наступна зміна: …», посилання на `/tsiny`, час. Без ніків.
- **Rationale**: FR-002, FR-012; ліміти Discord — 10 embed, 25 полів, 6000 символів на повідомлення.
- **Alternatives**: звичайний текст — гірше читається на телефоні; embed пересилається підписникам так само.

## R5. Звідки чернетки новин

- **Decision**: крок у `deploy.yml` після успішного деплою з `main` надсилає функції (дія `drafts`, секрет) верхній запис
  `src/data/changelog.json` (програма) і верхній запис нового `src/data/sitenews.json` (сайт). Функція створює
  чернетку, якщо `source_ref` (`changelog:<id>` / `site:<id>`) ще немає. Ручна новина — `source_ref = manual:<uuid>`.
- **Rationale**: FR-005; домовленість проєкту «журнал — лише про програму» лишається, а зміни сайту отримують свій файл
  того самого формату (`id`, групи `added / changed / fixed`). Повторний деплой не дублює чернетку.
- **Alternatives**: генерувати новину з комітів — мова розробника, не гравця; відкинуто.

## R6. Перегляд «як у Discord»

- **Decision**: `format.ts` повертає тіло повідомлення Discord (`{ content, embeds }`); сайт рендерить той самий об'єкт
  компонентом `DiscordPreview` (темний фон, смуга кольору embed, заголовок, поля). Одне джерело — перегляд збігається з
  відправленим.

## R7. Права й секрети

- **Decision**: таблиці бота — RLS лише `is_admin()`; функція приймає або сесію `admin` (кнопки в адмінці), або
  `x-sync-secret` (cron і CI) — як `rules-sync`. `DISCORD_BOT_TOKEN` лише в секретах функції; сайт токена не бачить.
- **Rationale**: FR-008, FR-010, SC-006; конституція «Безпека й секрети».

## R8. Що робить власник (без коду)

1. Discord Developer Portal → New Application → Bot → токен → `npx supabase secrets set DISCORD_BOT_TOKEN=…` (не в чат).
2. Запросити бота на сервер Q-Hub з правами «Send Messages», «Embed Links», «Manage Messages» (для crosspost у
   власному каналі-оголошенні достатньо «Send Messages» + «Manage Messages»).
3. Створити канали `#ціни` і `#новини` типу «Оголошення» (Announcement).
4. Увімкнути `pg_cron` і `pg_net`; задати `DISCORD_SYNC_SECRET` у функції й GitHub Secrets.
